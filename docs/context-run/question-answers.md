# Exercise Answers: Managed Context Run (draft for review)

## Question 1: Where did context management break down or hold up better than expected, and what did that tell you about the technique?

Context management held up better than I expected around the requirement change. After the Boundary A message in M3, the agent named the retired rules (R3 and R4) and dropped the "Deferred: security" section. It ranked all four security findings above the correctness bugs and kept the table at exactly six rows. It never applied a retired rule again, and its own self-audit at M8 agreed. The strongest test was Phase 3: two versions of the ranked table were in context, and the agent still picked the top three from table v2 (F9, S1, S2), not from table v1. In M7 it used table v2's ranks 4 to 6 (S3, F1, F2) even though my wording ("F-IDs") could have pulled it toward the F-numbered findings. It also coped well when I accidentally pasted M6 twice: it recognized the repeat and did not redo the work. The breakdown came from a different source than rule drift. In Phase 1 the agent claimed that `deleteById` on a missing review causes a 500 error, which is not true for Spring Data JPA 3.x in this project. That incorrect finding (F2) passed through both boundaries and the summary unchanged and ended up in the final report at rank 6. This told me that explicit boundaries and summaries are very good at keeping *rules* current, but they do not check *facts*. They carry forward whatever the session believes, errors included. The same thing happened on a smaller scale with the observation that S1 is tracked under FEATURES.md item 2, which was dropped between phases.

## Question 2: Why did you place your explicit context boundaries where you did?

I placed Boundary A at M3 because that is where the requirements changed. The main risk was that the agent would keep using the Phase 1 rules from earlier in the conversation: deferring security and allowing eight findings. The boundary message said Phase 1 was complete and table v1 was final. It named which rules stayed active (R1, R2, R5), which were replaced (R3 by R3', R4 by R4'), and the new rule R6. It also said what to carry forward: table v1 with stable IDs. This separated the "find and rank bugs" phase from the "re-prioritize with security first" phase. I placed Boundary B at M6 because the type of work changed from ranking findings to designing tests, and by then two conflicting versions of the ranked table were in context. That boundary named the summary file's table v2 as the authoritative ranking and repeated that R3 and R4 were retired. It also said no rules changed in Phase 3, so the agent would not go looking for new ones. In both places, the boundary marked a point where either the active constraints or the active artifact changed, which is where I expected drift to happen.

## Question 3: What information did your proactive summary preserve?

The summary at the end of Phase 2 (`docs/context-run/summary-after-phase2.md`) preserved the most important information well. It quoted all six active rules word for word with their R-numbers, including the new R6. It listed both retired rules word for word with what replaced each one. It included the full table v2 with file:line references and quoted evidence. It recorded that F3 to F8 were dropped only because of the six-item cap and were still valid. It also carried the maintainability items from Phase 1 into its unresolved questions, along with good open questions about whether the cap would persist. These were the details that mattered most for Phase 3, because the test recommendations depended on the exact current ranking and the current rules. The summary was weaker in three places. Its "Current goal" described the checkpoint itself rather than the overall review task. Its "Next planned action" was only "await the user's direction", because I had never told the agent that Phase 3 would be test recommendations; that was a gap in my plan. It also dropped the earlier observation that S1 belongs to FEATURES.md item 2. Finally, it repeated F2's incorrect "crashes with a 500" claim as fact, so the summary was accurate to the session but not to the code.

## Question 4: How well did the agent respond to the requirement change?

The agent responded very well to the requirement change. It applied the new rules immediately and correctly: it retired R3 and R4 by name, ranked all security issues above correctness issues, cut the table to exactly six findings, and read `User.java` because of the new scope rule. Reading `User.java` produced the most important new finding, F9: `POST /api/users` returns the user's plaintext password in its response. The agent also updated the earlier artifact rather than starting over. It re-ranked table v1 into table v2, kept every existing ID stable, gave the new finding a new ID, and wrote a moved/added/dropped note for all twelve IDs. It did not simply delete the findings that were cut; it marked them as still valid. Later work followed the new requirements consistently. Phase 3 test recommendations targeted table v2's top three, the coverage check used table v2's ranks 4 to 6, and the final report contained only the six-row, security-first table with no leftover deferred-security section. The one weakness is that the re-ranking kept F2 at rank 6 without re-checking whether its Phase 1 claim was correct, so an earlier error survived the update. The requirement change was handled well; the earlier analysis it carried forward was not re-verified.
